# 形态识别与动态拆分规则

拆分信号与语言无关。下面的数值都是待审启发式:用来决定要不要评估下拆,不强制生成或删除文档。默认只生成根篇;仅在子目录有独立、可验证的操作约束时增加子篇。拆分建议须说明证据。不得为不存在的目录创建篇目。

## 核心原则:先精简，再按独立约束拆分

体系不设固定层数,也不把任一语言的「根 / 组 / 包」当成层数上限,而是一张按代码量与扇出动态生长的树:

> 每个目录节点独立问一句:**"以我一篇 40–130 行的容量,能否讲清我子树的契约?"**
> 讲不清 → 按模块拆出子篇,我退化为**路由篇**(速览表 + 跨边界契约 + 下钻链接);
> 讲得清 → 保持叶子篇,契约写在我正文里。

递归在任意深度进行。典型场景:目录 A 子树超过 ~100k 加权代码量,或直接子项多到路由篇装不下——必须按模块切开 A 的覆盖面,每个模块一篇 AGENTS.md,A 篇只剩「模块速览表 + 模块间契约 + 导引」。

路由篇导航表每个子项约一行。在 40–130 行预算下,**>~15 个直接子项**(子目录或平铺文件逐个入表)就不可能再容纳跨边界契约,必须再插入一层。这一层落在目录上:已经有大量子目录就做分层,只有平铺文件就先按功能分子目录,见 [restructure.md](restructure.md)。把多个子项挤进少数单元格,行数看起来合规,仍然算没下钻。加权代码量低、父篇提到过这个目录,都不能取消文件扇出或目录扇出。

## 节点拆分触发条件(满足其一时评估)

| 信号 | 阈值 | 依据 |
|---|---|---|
| 节点子树**加权代码量** | **>30k** → 建议评估拆分;15k–30k → 有 ≥3 个可独立说明的子模块才拆 | 单篇容量装不下子树契约;按语言密度加权,见下。代码量低不能取消下面的扇出 |
| 公开契约数 | **>20 个公开条目**(入口符号 / 导出面合计)或 >8 个子模块各带公开面 | 与语言体量无关的第二轴:一行 DSL 也可能契约密集。怎么数见「公开条目」 |
| 子节点数 | **>8** 个有实质内容的子目录 → 评估速览表是否装得下;**>~15** → 目录扇出,必须提议插入分组层 | 路由篇装不下直接子项;子目录已经存在也不取消;与加权代码量无关 |
| 目录内**直接平铺源文件数** | **>~20** 个非测试源文件直接位于节点目录下 | 文件扇出。低加权代码量与父篇提及都不能取消。评估按功能分子目录(见 [restructure.md](restructure.md)),而不是写一篇大文档;其余位置信号见 [layout.md](layout.md) |
| 单篇正文 | >130 行且其中**任一节 >40 行** | 该节该下沉成子篇了 |
| 契约独立度 | ≥3 个子模块各有独立的「本地契约」需求(互相能单独说清,接口小而行为多——参考 mattpocock/skills@codebase-design 的 Depth/Seam 判据) | 挤在父篇会膨胀 |

### 语言密度系数(加权代码量 = Σ 各语言代码行 × W)

不同语言的「每行信息量」差数倍,裸 LOC 一刀切会误判(10k 行 Java ≈ 4k 行 Python 的行为量;50k 行 JSON 几乎没有契约)。以 Rust/Python 行为 1.0 基线:

| W | 语言 |
|---|---|
| 1.1 | C |
| 1.0 | Rust, Python, Ruby |
| 0.9 | Swift, TypeScript |
| 0.8 | Go, JS, C++, PHP |
| 0.7 | C#, Kotlin, Java(声明冗长但契约清晰) |
| 0.6 | 样板重的框架代码(如 Android View 层、DTO 生成) |
| 0.2–0.3 | HTML/CSS/SQL 迁移脚本 |
| 0.05–0.1 | JSON/YAML/TOML/XML 等配置与数据(体量再大也不构成分拆理由,只数文件数) |
| 0 | 注释、lock 文件、生成代码(`target/`、`*.pb.*`、snapshot) |

系数表是**先验**,需依据实测审查。

统计命令(tokei 表列序:Language Files Lines Blanks Comments Code,cloc 同理取 Code):

```bash
tokei <node> 2>/dev/null | awk '/^Total|^Artifacts|^-/{exit} $6 ~ /^[0-9,]+$/ {gsub(/,/,"",$6); print $1, $6}' | \
python3 -c 'import sys
W={"C":1.1,"Rust":1.0,"Python":1.0,"Ruby":1.0,"TypeScript":0.9,"Swift":0.9,"Go":0.8,"JavaScript":0.8,"C++":0.8,"CPP":0.8,"PHP":0.8,"C#":0.7,"CSharp":0.7,"Kotlin":0.7,"Java":0.7,"HTML":0.25,"CSS":0.25,"JSON":0.08,"YAML":0.08,"TOML":0.05,"XML":0.08,"Markdown":0}
s=0
for line in sys.stdin:
    lang, code = line.split(); s += int(code)*W.get(lang,0.5)
print(int(s))'
```

两者都不在 PATH 时(不要求用户安装):退回扩展名统计并标注「未加权近似值」——

```bash
git ls-files <node> | awk -F. 'NF>1{c[$NF]++}END{for(k in c)print c[k],k}'   # 各扩展名文件数
git ls-files <node> | xargs wc -l | tail -1                                     # 总量(未加权)
```

未加权口径下阈值放宽:报告里写明「建议装 tokei 复核」。

合并(反向)触发:节点子树收缩到 **<10k 加权代码量且 <2 个有内容的子节点**,或其下所有子篇合计 <40 行 → 子篇收回父篇表格一行。功能子目录收缩到 **<3 个源文件**时同理,是塌缩节点。**目录合回同样是代码搬移**,走 restructure 门禁执行,不经 sync。护栏:子节点 <2 时不设篇层;**只为「会漂移的边界」拆**,纯转发无契约的中间层不加篇。

## 第一步:形态识别(纯 manifest 扫描)

词汇替换见 [templates.md](templates.md)。下表只判断形态,不附带行数阈值。同一仓库出现多份 manifest 时,按子树分别识别,不选一种语言当全仓词汇。

| 信号 | 判定 |
|---|---|
| `Cargo.toml` 有 `[workspace].members` | Rust workspace。仅当存在 `crates/<组>/<成员>` 这类嵌套时,中间目录才是「组」 |
| `package.json` 有 `workspaces` / `pnpm-workspace.yaml` / `turbo.json` | JS/TS monorepo |
| `pyproject.toml` + `src/<pkg>/` 布局 | Python 单包(域看 `src/` 子包) |
| `go.work`,或多个 `internal/` 大目录 | Go |
| `settings.gradle*` / `settings.gradle.kts`,或 Maven `<modules>` | JVM 多模块 |
| `*.sln` | .NET |
| `Package.swift` | SwiftPM |
| `CMakeLists.txt` / `meson.build` | C/C++。目录语义弱于包管理器,不臆造 target 层 |
| `composer.json` | PHP |
| `Gemfile` 且有 `lib/` | Ruby |
| 父目录下多个各带 `.git` 的子目录 / `.gitmodules` | **多仓工作区** → 需要模板 D 路由篇 |

**文件扇出**:某目录直接平铺非测试源文件 >~20 时,拆分的前提是按功能划分子目录。低加权代码量、父篇已经点到这个目录,都不取消。audit 输出重组类提案(引用共现 / 命名前缀 / 测试对应 / git 共变 / 跨树同名),经**逐目录人工批准**后由 restructure 执行 `git mv`(见 [restructure.md](restructure.md))。

**目录扇出**:直接有实质内容的子目录 >~15 时,即使子目录已经存在,也输出分层类提案,把这些子目录收成 2–8 个分组目录。用户拒绝搬移时只报告,不为尚不存在的分组建篇。

sync 永不移动代码。错位文件、根目录杂物、碎目录等其余位置整理信号见 [layout.md](layout.md),同样以搬移提案落地。

## 第二步:规模统计

优先 `tokei` / `cloc`;没有则:

```bash
git ls-files -z | xargs -0 wc -l | tail -1                    # 总量
for d in <候选节点目录>; do git ls-files "$d" | xargs wc -l | tail -1; done   # 各节点子树量
```

记录:每节点子树加权代码量、直接子目录数、直接平铺源文件数、每子树公开条目数。公开条目只数入口面,不把每个源文件都算进去:

| 语言 | 入口面 |
|---|---|
| Rust | 入口文件里的 `pub fn` / `pub struct` / `pub trait` / `pub enum` / `pub type`(通常是 `src/lib.rs` 与再导出) |
| TS/JS | 入口或 barrel 文件里的 `export` |
| Python | `__all__`;没有则数非下划线开头的公开函数与类 |
| Go | 大写开头的导出标识符 |
| JVM / C# | `public` 类型 |
| Swift | `public` / `open` |
| C/C++ | 公开头文件里的对外声明 |
| 其它 | 该语言的包入口,口径写进报告 |

## 第三步:DFS 生长算法(init 与 audit 共用)

```
walk(节点=仓库根, 父篇=无):
  先看扇出,再看加权代码量与公开契约。扇出不因代码量低而跳过
  直接平铺源文件 >~20
       → 重组类候选:按 restructure.md 聚类,批准后再继续 walk;未获批则只报告
  直接有实质内容的子目录 >~15
       → 分层类候选:把现有子目录收成 2–8 个分组,批准后再继续 walk;
         未获批则只报告,不为尚不存在的分组建篇
  两条扇出同时成立时,两份提案都写
  其余信号不超 → 该节点是叶子:按模板 C 写一篇(根节点除外,见下)
  其余信号超载 → 按已有模块/子目录定出 2–8 个分组
         每组递归 walk;该节点自身按模板 B 写一篇路由/速览篇
根节点恒为模板 A(常驻篇):导航表覆盖其全部分组,自身不再下钻
```

典型收敛结果(自然语言对照,不是硬规则):

| 全局形态 | 会收敛出的树 |
|---|---|
| <10 源文件 / <3k 加权 | 只有根篇(模板 A 精简 ≤80 行) |
| 3–9 个包,无深层结构 | 根 + 目录篇(两层) |
| ≥10 个包或模块 / >30k 加权 | 根 + 组篇 + 成员篇(三层) |
| 某成员内部 >30k 加权,或任一节点扇出超限 | 该节点下继续长出下一层 |
| 多仓工作区 | 最外加一层模板 D 路由篇 |

## 单篇行数预算(与深度无关,按角色)

| 角色 | 预算 |
|---|---|
| 常驻根篇 | 120–180(硬上限 200);导航表与映射表必须留在根篇,超限先下拆**细则** |
| 路由篇(任意深度的非叶节点) | 40–130 |
| 叶子篇(成员/目录) | 40–90 |
| 多仓路由篇(模板 D) | ≤120 |

## 无 git / 全新项目

init 只依赖文件系统,可跑。sync 的 churn 与锚点信号缺失 → 退化为 audit 式全量比对(代码实体集合 vs 文档登记集合的差集)。

## 已测锚点

行数预算只在一个 45-crate 的 Rust workspace 上对过:根篇 178 行、组篇 40–128、成员篇 50–71、多仓路由篇 115。其它生态尚未实测。这些数字是启发式的对照,不是层数上限,也不把该仓库的树形套到别的语言上。
